# Drifting Sea 상영 재설계

작성일: 2026-09-22. 상태: 단계별 구현 완료. 실제 구현·검증 결과는 implementation-stages.md 및 screening-operations.md 참조.
아래에서 '확정 요구'는 사용자 요청이며, '제안'은 아직 사용자 확정 전이다.

## 1. 확정 요구와 용어

- 기본 영상 반복 재생 유지. 교체되는 영상의 총길이를 자동으로 반영한다.
- 기본 영상 종료 60초 전부터 종료까지 서서히 페이드아웃한다. 60초는 쉽게 수정할 수 있어야 한다.
- 기본 영상이 완전히 사라진 뒤 30초 후 다음 반복을 시작한다. 30초도 쉽게 수정할 수 있어야 한다.
- 페이드아웃 시작과 동시에 `해파이 오브젝트`가 서서히 나타난다. 사용자 제공 예정인 해파리 3D 모델을 사용한다.
- 영상 소멸 후 대기 시간 동안 해파이를 유지하고 다음 영상 시작 순간 이전 회차의 해파이 오브젝트를 전부 즉시 제거한다(사용자 확정). 퇴장 페이드는 없다.
- 태블릿에서 `문장트리거`를 받으면 `트리거영상`을 기본 영상 위에 반투명하게 표시한다. 투명도를 쉽게 조절한다.
- 트리거영상은 중앙 대신 상·하·좌·우 가장자리/모서리 주변에 자연스럽게 나타나며 매번 동일 위치에 고정하지 않는다.
- 한 회차의 기본 영상 전체 재생 기간에 받은 문장트리거 횟수로 해파이 개체 수를 결정한다.
- 해파이는 바닷속을 보는 듯한 깊이감을 가져야 하며 화면에서 실제로 식별되어야 한다.
- 기존 시작 시 전체화면, Esc로 창 모드 전환하며 재생 유지, F로 전체화면 복귀 동작을 보존한다.

## 2. 한 회차의 시간 설계

영상 메타데이터의 실제 길이 D, 종료 전 페이드 시간 F, 완전히 사라진 뒤 유지 시간 H를 사용한다.
기본값은 F=60초, H=30초. 현재 영상 D=311.266667초.

| 현재 영상의 경과 시간 | 기본 영상 | 해파이 오브젝트 | 트리거 집계 |
| --- | --- | --- | --- |
| 0 ~ 4:11.27 | 정상 재생 | 신규 개체는 숨김 | 현재 회차 누적 |
| 4:11.27 ~ 5:11.27 | 100% → 0% | 0% → 100%로 출현 | 현재 회차 계속 누적 |
| 5:11.27 ~ 5:41.27 | 완전 투명, 종료 상태 | 유지 확정 | 다음 회차 대기분으로 분리 제안 |
| 5:41.27 | 0초에서 다음 회차 시작 | 이전 회차 개체 전부 즉시 제거 | 새 회차 시작 |

상태 흐름: 준비 → 정상 재생 → 영상/해파이 교차 페이드 → 해파이 유지 → 다음 영상 재생.

- HTML video의 즉시 반복 옵션 대신 상영 컨트롤러가 반복을 관리해야 30초 대기가 가능하다.
- 영상 진행 기준은 실제 currentTime이다. 로딩 후 경과한 벽시계 시간으로 영상 페이드를 계산하지 않는다.
- F는 D 이하로 제한한다. 영상이 60초보다 짧으면 시작부터 끝까지 페이드한다.
- F=0은 영상 종료 시 즉시 숨김, H=0은 종료 직후 다음 회차 시작으로 정의한다. 음수/비정상 값은 거부한다.
- 진행률 p=clamp((currentTime-(D-F))/F,0,1), 완만한 곡선 s=p²(3-2p)를 적용하여 영상 alpha=1-s, 해파이 그룹 alpha=s로 제안한다.
- ended 처리에서 영상 alpha=0을 강제하고 실제로 완전 투명 상태를 표시한 뒤 H의 대기를 시작한다. 프레임 누락이나 버퍼링으로 너무 일찍 반복하지 않는다.
- 대기 시간은 단조 증가 시계로 관리한다. 탭이 숨겨지면 남은 시간을 보존해 복귀 시 이어가는 것을 제안한다. 창 모드 전환만으로는 중단하지 않는다.
- 다음 영상의 첫 프레임이 준비될 때까지 해파이 화면을 유지한다. 재생 실패 시 개체와 회차 집계를 조기에 지우지 않는다.
- 다음 영상의 첫 프레임을 표시하는 시점에 이전 회차 해파이 렌더링을 전부 끈다. 제거와 새 회차 시작을 동일한 전환으로 처리해 잔상이나 한 프레임 겹침이 없도록 한다. 기존 3초 교차 전환 제안은 삭제하며 기본 영상은 정상 불투명도로 시작한다. 새 회차 해파이는 해당 영상의 종료 전 페이드 구간까지 표시하지 않는다.

## 3. 쉽게 수정하는 운영 설정

제안: 상영 화면과 분리된 한국어 운영 설정 화면 + 단일 설정 JSON을 둔다. 코드를 고치거나 재빌드하지 않고 조절한다.

| 한국어 항목 | 초기값 | 적용 규칙 |
| --- | --- | --- |
| 종료 전 페이드 시간(초) | 60 | 다음 회차부터 |
| 완전 페이드 후 유지 시간(초) | 30 | 다음 회차부터 |
| 트리거영상 불투명도(%) | 35, 제안 | 미리보기 가능, 이후 트리거부터 |
| 트리거 1회당 해파이 수 | 1, 제안 | 다음 회차부터 |
| 최소 해파이 수 | 1, 제안 | 무참여 회차에도 존재 보장 |
| 최대 해파이 수 | 성능 측정 후 확정 | 초과 트리거도 집계는 계속 |
| 동시 트리거영상 수 | 3, 제안 | 디코더 부하 제한 |
| 해파이 최소 화면 크기/밝기 | 모델·프로젝터 확인 후 확정 | 화면에서 식별 가능하도록 제한 |

투명도라는 말의 혼동을 막기 위해 UI에는 '불투명도: 0%=안 보임, 100%=원본 밝기'를 표시한다.
영상 총길이는 편집값이 아니라 읽기 전용 자동 감지값으로 표시하고 페이드 시작 시각을 함께 보여준다.
운영 설정에는 현재 적용값/다음 회차 적용값, 기본값 복원, 설정 내보내기·가져오기를 제안한다.
정적 배포에서는 브라우저 설정이 다른 기기에 자동 전파되지 않는다. 상영 기기가 설정의 주체이며 JSON 가져오기/배포로 공유한다. 브라우저 저장이 불가능하면 파일 기반 기본값으로 동작한다.

## 4. 문장트리거 전달과 집계

현재 Game Poem은 단어/문구 배치 상태를 40ms 단위로 묶어서 전송한다. 가장자리로 보내기에는 direction/sentAt이 있으나 독립적인 문장 완료 이벤트는 없다. 상태 전송 횟수 또는 active 항목 수를 참여 횟수로 사용하면 안 된다.

발생 동작 확정: 태블릿에서 문구를 중앙 문장에 추가할 때마다 1회.
새로 추가하는 클릭·터치·드래그·키보드 조작을 동일하게 처리한다. 중앙 문장 안에서 순서만 바꾸기, 제거, 화면 가장자리로 보내기, 일반 위치 이동은 제외한다. 제거 후 다시 추가하면 새로운 1회로 해석한다.
현재 joinSentence는 재배치에도 호출될 수 있으므로 호출 횟수를 세면 안 된다. 조작 전 중앙 문장에 없던 문구가 조작 완료 후 포함되는 전이를 이벤트로 만든다. 드래그 취소는 발생시키지 않는다.

제안하는 사건 단위:

- sentence-trigger: eventId, senderId, senderSequence, room, protocolVersion, phraseIds, direction(선택).
- 상영 화면이 최종 수신·승인 주체다. eventId로 중복 제거하고 회차당 정확히 한 번 집계한다.
- 브로드캐스트와 PeerJS 양쪽으로 같은 이벤트가 도착해도 1회만 처리한다. ack·연결 복구·위치 변경 메시지는 집계하지 않는다.
- 태블릿의 미확인 이벤트 큐와 재전송/ack를 둔다. 현재 '마지막 상태만 보관'하는 방식으로는 빠른 연속 트리거를 보존할 수 없다.
- 정상 재생/페이드 중 수신·승인된 이벤트는 현재 회차에 귀속한다. ended로 회차를 닫은 이후 수신한 이벤트는 다음 회차 대기분으로 분리하는 안을 제안한다.
- 연결 지연으로 늦게 수신된 이벤트를 보낸 시각에 소급 배정하지 않는다. 태블릿/상영 기기의 시계 차이를 집계 근거로 사용하지 않는다.
- 대기 중 이벤트도 ack하고 다음 회차에 정확히 한 번 반영한다. 트리거영상은 새 기본 영상이 시작되면 순서대로 재생하는 안을 제안한다.
- 이벤트 큐의 보존 기간/최대 길이와 과다 입력의 유효 기준은 구현 전 확정한다. 화면 큐가 포화되어도 집계 이벤트를 조용히 누락하지 않는다.
- 회차 경계는 상영 컨트롤러 한 곳에서 처리한다. 회차 ID, 승인 순서, 누적 횟수, 중복 제거 기록을 유지한다.
- 새로고침은 신규 상영 세션 시작으로 제안한다. 이전 세션 재전송 이벤트를 새 회차로 잘못 집계하지 않도록 sessionId 핸드셰이크를 추가한다.

상영 페이지가 시간·개수·합성의 주체이며, 태블릿은 입력을 담당한다. 기존 투명 iframe은 통신 어댑터로 활용 가능하지만 해파이와 트리거영상은 상영 페이지에서 렌더링한다.
iframe 어댑터 사용 시 postMessage의 origin, source, room, 메시지 구조를 검증한다. 로컬 5189/5190과 배포 경로를 모두 명시적으로 지원한다. 기존 텍스트/2D 효과의 유지 여부는 별도 확인한다.

## 5. 트리거영상 합성

- 기본 영상과 같은 표시 영역을 사용한다. 브라우저 창의 검은 여백이 아닌 실제 영상 영역 기준으로 배치한다.
- 상·하·좌·우 가장자리 띠와 네 모서리를 후보 영역으로 두고 중심 영역 및 하단 자막 안전 영역을 제외한다.
- 매 이벤트마다 후보 위치·크기·가벼운 이동을 결정한다. 직전 위치 반복과 활성 오버레이 간 과도한 겹침을 억제한다.
- 방향 정보가 있으면 해당 방향에 가중치를 주되 좌표는 고정하지 않는다. 모델/영상 비율에 따라 화면 밖으로 전체가 잘리지 않도록 제한한다.
- 부드러운 가장자리 마스크와 등장/퇴장 페이드를 기본 사용한다. 사각형 영상 경계가 선명하게 드러나지 않게 한다.
- 기본 합성은 normal alpha로 제안한다. screen 합성은 제공되는 영상이 검은 배경일 때만 비교 검토한다.
- 트리거영상은 무음·1회 재생, 파일 길이에 맞춰 퇴장하는 것을 제안한다. 입력 파일·길이·알파 채널 유무는 미제공 상태다.
- 동시 재생 수와 큐 길이를 제한한다. 초과 이벤트의 모든 영상을 지연 재생할지, 시각 효과만 묶을지는 사용자 확정이 필요하다. 집계 수는 시각 슬롯 수와 독립적이다.
- 기본 영상이 페이드할 때 트리거영상도 기본 영상 그룹 alpha를 곱해 사라지게 하는 안을 제안한다. 종료 직전 새 트리거영상은 짧게 보일 수 있으나 해파이 집계에는 포함한다.

## 6. 해파이 오브젝트 개수와 가시성

제안식: N=min(Nmax, max(1, k×C)). C=현재 회차의 중복 제거된 문장트리거 수, k=기본 1.
0회도 최소 1개, 상한 적용은 사용자 승인 전 제안이다. 단순히 '트리거 0회=0개'로 두면 화면에 반드시 해파이를 보여야 한다는 요구와 충돌한다.

- 페이드 시작 시 그때까지의 C로 개체를 나타낸다. 마지막 구간의 새 트리거는 개체를 부드럽게 추가한다. 영상 종료 시 최종 개수를 확정한다.
- 최종 전체 횟수를 페이드 시작 전에 알 수는 없다. 따라서 '시작 시 이미 최종 수량 고정'과 '마지막 1분까지 모두 집계'를 동시에 요구하지 않는다.
- 모델은 미리 로드해 숨겨 두고 등장 시점에 네트워크 로딩을 시작하지 않는다. 사용자 모델은 GLB/glTF 형태를 제안하되 파일을 받은 뒤 재질·애니메이션·축·크기·폴리곤 수를 점검한다.
- 카메라를 고정하고 근경/중경/원경의 실제 z 깊이에 분산한다. 원근 크기, 이동 속도 차이, 제한된 안개 및 명암으로 수중 깊이를 표현한다.
- 화면 좌표에서 먼저 읽을 수 있는 위치를 정한 뒤 깊이별 3D 위치로 변환한다. 무작위 3D 배치 후 카메라 밖에 가려지는 방식은 피한다.
- 각 개체의 화면상 최소 크기, 최소 대비, 화면 안쪽 안전 여백을 보장하고 중첩을 제한한다. 최소 1개는 중·근경의 명확한 식별 위치에 둔다.
- 낮은 속도의 부유와 모델 애니메이션을 사용한다. 이동 후에도 가시 영역을 벗어나지 않도록 제약한다. 원경도 안개에 완전히 묻히지 않도록 한다.
- 모델 전체를 자식 메시마다 따로 페이드하면 반투명 재질이 겹쳐 밝기가 달라질 수 있다. 투명 3D 캔버스 전체를 그룹 페이드하는 안을 우선 검토한다.
- 재질 투명 정렬, 발광 과다, 깊이 버퍼, 촉수 애니메이션 비용을 실제 모델로 점검한다. 스키닝 모델은 단순 인스턴싱을 전제로 하지 않는다.
- 현재 exports/haepai/haepai-52k-source.glb가 발견되어 런타임 복사본을 연결했다. 해당 모델의 화면 가시성은 확인했으며 전시장 시각 검증은 별도다. 모델 로드/WebGL 실패 시 명확한 해파이 실루엣 대체 이미지를 사용하도록 제안하되 대체 이미지도 별도 준비해야 한다.
- 페이드 시작 순간 alpha=0이고 이후 점진 출현하므로 '항상 보임'은 정상 영상 전체 기간이 아니라 해파이 등장 구간의 가시성 요구로 해석한다. 다른 의미라면 확인 필요.

## 7. 레이어·자막·오디오 정책

아래에서 위 순서: 어두운 수중 배경 → 기본 영상 → 트리거영상 → 해파이 3D → 기존 상호작용 텍스트(유지 시) → 자막 → 운영 UI.
전체 컨테이너를 페이드하지 않는다. 기본 영상/트리거영상 그룹과 해파이 그룹을 각각 제어해야 해파이가 함께 사라지지 않는다.

- 자막은 기본 영상 시간에 맞추고 기본 영상과 함께 페이드해 종료 후 지운다. 기존 상호작용 텍스트도 유지한다면 종료 전 페이드 대상으로 묶는 것을 제안한다.
- 현재 사운드는 영상과 무관하게 약 26초 루프로 재생된다. 이번 요구는 영상 페이드이므로 사운드는 대기 구간까지 연속 유지하는 안을 제안한다. 음악까지 페이드할지는 별도 확정한다.
- 트리거영상 무음 정책으로 복수 오디오 중첩을 피한다.
- Esc/F는 전체화면 상태만 바꾼다. 재생 시각, 대기 타이머, 카운터, 해파이 배치가 초기화되어서는 안 된다.

## 8. 설계 점검과 구현 전 검증 기준

| 항목 | 통과 기준 / 확인 사항 |
| --- | --- |
| 영상 길이 변경 | 짧은/긴 영상으로 교체해도 종료 기준 상대 시간으로 페이드 시작 |
| 기본 주기 | 현재 영상에서 4:11.27 페이드 시작, 5:11.27 완전 소멸, 이후 30초 유지 |
| 회차 반복 | 10회 이상 반복해도 시작/종료 중복, 타이머 중첩, 누적 드리프트 없음 |
| 해파이 즉시 제거 | 다음 영상의 첫 프레임부터 이전 회차 해파이가 하나도 보이지 않음. 퇴장 페이드나 잔상 없음 |
| 버퍼링·숨김 | 영상 정지 시 페이드만 선행하지 않으며 대기 시간을 소진해 화면을 건너뛰지 않음 |
| 이벤트 정확성 | 동일 ID 중복, 양 경로 도착, 재연결 재전송은 1회; 서로 다른 ID는 각각 집계 |
| 경계 이벤트 | 페이드 직전·종료 직전·대기 중·새 회차 시작 시 귀속이 일관됨 |
| 빠른 입력 | 태블릿 큐에서 이벤트가 마지막 상태에 덮어쓰여 사라지지 않음 |
| 0회/1회/다수 | 승인된 개수 공식대로 표현하고 최소 가시성과 성능 상한 준수 |
| 모서리 합성 | 반복 입력마다 위치 변화, 중앙 회피, 자막 보호, 검은 여백 회피 |
| 해파이 가시성 | 목표 프로젝터·밝기에서 중경/근경 개체와 원경 깊이감 확인 |
| 모델/영상 실패 | 기본 영상 지속 및 대체 표시; 승인된 이벤트 집계는 시각 자산 실패로 유실되지 않음 |
| 전체화면 | 시작 → Esc → F 동안 영상·사운드·회차 연속; 일반 브라우저에서 확인 |
| 설정 변경 | 잘못된 값 거부, 다음 회차 적용 시점 명시, 운영자가 코드 없이 변경 |
| 배포 | JS/JSON/모델의 캐시 버전 일치. 고정 파일명 revision:null 및 쿼리 캐시 불일치 점검 |

위 표는 초기 설계의 수락 기준이다. 이후 사용자 구현 지시에 따라 진행했으며, 실제 통과 항목과 미검증 범위는 implementation-stages.md에 구분해 기록했다.

## 9. 확정이 필요한 연출 결정

1. 문장트리거 발생 동작은 확정: 문구를 중앙 문장에 추가할 때마다 1회. 재배치 제외·제거 후 재추가 집계는 이 정의에 따른 설계 해석이다.
2. 대기 중 해파이 유지 및 다음 영상 시작 순간 전부 즉시 제거는 확정. 퇴장 시간 설정은 두지 않는다.
3. 0회에도 최소 1개를 보여주는 규칙, 1회당 개체 수, 성능 상한.
4. 대기 중 입력의 다음 회차 귀속과 지연 오버레이, 과다 입력 시 시각 효과 처리.
5. 사운드 연속 유지, 자막/기존 텍스트 페이드, 트리거영상 무음 정책.
6. 해파이 모델과 트리거영상 파일.
