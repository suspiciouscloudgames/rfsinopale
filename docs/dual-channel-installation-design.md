# Windows 2채널 설치 설계

작성: 2026-09-23. 아래 내용은 구현 기준 설계다. 이후 Electron 구현을 진행했으며 실제 완료·미검증 범위는 [단계별 구현 기록](dual-channel-implementation.md), 실행 방법은 [운영 안내](dual-channel-operations.md)를 참조한다.

## 1. 확정 요구와 설계 가정

확정 요구:
- Windows에서 두 디스플레이에 각각 다른 영상을 전체화면으로 재생한다. 두 번째 영상은 assets/floorVideos/floor.mp4로 제공되었다.
- 해파이 오브젝트는 두 채널 사이를 하나의 화면처럼 이동한다.
- 두 화면은 위아래로 배치하고 함께 페이드하여 해파이 구간으로 전환한다(사용자 확인).
- 위 화면에는 기존 영상 A, 아래 화면에는 새 영상 B를 배치한다(사용자 확인).
- 현재 프로젝트를 기반으로 구현하며 Electron 포팅의 적합성을 검토한다.

초안 가정(사용자 확정 전): Windows PC 한 대, GPU의 두 출력, 확장 디스플레이 모드, 위아래로 이어진 평면 화면. 예시는 1920×1080 두 대다. 실제 화면 크기·해상도·주사율·DPI·간격·프로젝터 중첩 여부는 아직 모른다. 2 PC, 코너 설치, 엣지 블렌딩은 추가 설계가 필요하다.

두 채널의 공통 페이드·해파이 전환은 확정이다. A=위/B=아래 배치는 확정이다. 영상 A를 회차 기준으로 삼는 방식을 제안하며 화면 매핑은 운영 설정으로 관리한다. 서로 다른 영상 길이 처리와 오디오 B의 사용 여부는 미정이다. 아래 정책은 확정 요구가 아니라 구현 가능한 기본안이다.

## 2. 기술 선택

**Electron + 기존 Three.js 상영 코드 + 디스플레이별 출력 창 두 개를 기본안으로 제안한다.**

| 방식 | 적합성 | 판단 |
|---|---|---|
| 일반 브라우저 창 두 개 | 기존 코드는 재사용 가능하지만 화면 배치·부팅·복구를 별도로 운영해야 한다 | 개발용 미리보기 유지 |
| Electron 출력 창 두 개 | 각 출력 지정, 로컬 자산, 창 장애 감지, 설정 저장을 한 앱에서 처리 가능 | 기본안 |
| Electron의 큰 무테 창 한 개 | 하나의 장면·렌더 루프로 전체 화면 연결이 간단하다. 서로 다른 DPI와 비정형 배치 대응이 까다롭다 | 동일 조건의 인접 화면에서 비교 검증할 대안 |
| Unity 등으로 재작성 | 가능하지만 현재 HTML 영상·Three.js·태블릿 통신을 다시 구현해야 한다 | 현재 요구만으로 전환할 근거 부족 |

Electron은 운영 껍데기를 제공한다. 앱을 Electron에 넣기만 해서는 공통 장면·회차·이벤트 동기화가 생기지 않는다. 기존 메인 3D 체험의 배포 번들을 역으로 복원할 필요 없이 편집 가능한 video/를 우선 포팅한다.

공식 API 근거: [screen](https://www.electronjs.org/docs/latest/api/screen), [BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window). 화면 열거·변경 감지와 창 배치/전체화면 제어에 사용한다.

## 3. 전체 구조

```text
태블릿 Game Poem
       │ 문장트리거 / 상태 / ack
       ▼
통신 어댑터 한 개 ──▶ 중앙 상영 컨트롤러(Electron main)
                       ├─ sessionId / roundId / count / pending
운영 설정 ────────────▶ ├─ 회차 상태·시간·공통 seed·해파이 목록
                       ├─ 화면 매핑·미디어 검증·복구·오디오 소유권
                       │
                 제한된 IPC
                 ┌─────┴─────┐
                 ▼           ▼
             출력 A         출력 B
             영상 A         영상 B
             장면 위쪽      장면 아래쪽
```

메인 프로세스는 상태만 관리하고 WebGL 렌더링·비디오 디코딩은 각 renderer에서 수행한다. 렌더러는 표시 역할이며 트리거를 독자 집계하거나 회차를 단독 시작하지 않는다. 통신 어댑터는 한 번만 접속하여 동일 room의 host 중복을 방지한다.

별도 운영 창은 개발 시 사용하며 설치에서는 트레이/명시적 운영 모드로 접근한다. 세 번째 모니터가 없어도 운영할 수 있어야 한다. 운영 UI를 여는 행위 자체가 어느 출력의 재생도 멈추면 안 된다.

## 4. 하나의 공간을 두 화면에 표시

### 좌표계 분리

1. Windows 데스크톱 좌표(DIP): 창을 어느 모니터에 놓는지 결정한다. 음수 좌표도 허용한다.
2. 렌더링 픽셀: 디스플레이 해상도와 렌더 해상도 배율로 결정한다.
3. 설치 공간의 논리 좌표: 해파이의 위치·크기·화면 연결을 결정한다. Windows 화면 번호 및 DPI와 독립적이다.

같은 크기의 FHD 상하 설치 예시(각 디스플레이 자체는 가로 방향):

```text
공통 논리 화면 1920×2160
┌────────────────────┐
│ A: 기존 영상 / 위  │ y=0..1080
│        ↑           │
├────────┼───────────┤ ← 하나의 해파이가 걸쳐 보이는 경계
│        ↑ 해파이    │
│ B: 새 영상 / 아래  │ y=1080..2160
└────────────────────┘
```

두 renderer에 동일한 장면 정의·카메라·조명·seed·애니메이션 시간을 제공한다. A는 위쪽 frustum, B는 아래쪽 frustum을 사용한다. Three.js PerspectiveCamera.setViewOffset(fullWidth, fullHeight, offsetX, offsetY, width, height)로 공통 카메라의 부분 영역을 렌더링한다. 단순히 같은 카메라를 두 번 띄우거나 카메라 위치만 옮기는 방식은 쓰지 않는다.

예시: A=setViewOffset(1920,2160,0,0,1920,1080), B=setViewOffset(1920,2160,0,1080,1920,1080). 실제 값은 논리 viewport 설정에서 생성한다. [Three.js 공식 설명](https://threejs.org/docs/pages/PerspectiveCamera.html).

해파이가 경계를 걸칠 때 같은 ID의 모델 일부가 양쪽 화면에 동시에 보인다. 화면을 넘었다고 개체를 삭제·생성하거나 개수를 다시 세지 않는다. 모델은 양쪽 GPU 컨텍스트에 로드되지만 논리 개체 수는 전체 1~16개다.

### 현재 코드의 변경점

- jellies.js의 Math.random 기반 roundSeed·mixer 시작 시점은 중앙 seed와 개체 ID에서 결정하도록 바꾼다.
- elapsed += dt 누적 대신 공통 showTime 및 spawnTime으로 위치와 애니메이션 시점을 계산한다. 각 창의 FPS 차이가 이동 속도 차이가 되면 안 된다.
- jelly-layout.js의 개별 화면 aspect 대신 전체 설치 aspect를 사용한다. 기존 대각선 경로는 아래→위 이동을 주축으로 하고 완만한 좌우 흔들림을 추가한다. 양쪽의 수평 경계를 실제로 통과하고 측면으로 너무 일찍 빠져나가지 않도록 전역 경로를 재설계한다. 전체 세로 FOV와 개체 크기를 함께 조정해 두 화면 연결로 개체가 작아지는 문제를 방지한다.
- 카메라 통과 개체는 전체 공간에 하나만 둔다. 초기 등장 지점은 아래쪽 B 내부를 기본 제안하며 경계 한가운데서 시작하지 않도록 운영 설정에 anchor를 둔다.
- fog·조명·재질·색상 출력 설정은 동일하게 유지한다. 자동 노출 등 채널마다 다른 처리는 피한다.
- 대체 SVG도 전역 위치/동일 ID를 사용한다. 한쪽만 모델 로딩에 실패하면 양쪽 모두 동일한 대체 모드로 전환하여 경계에서 형태가 바뀌지 않게 한다.
- 현재 .film의 16:10 크기 제한과 overflow에 해파이가 종속돼 있다. 화면 전체 stage 안에 로컬 영상 레이어와 전역 해파이 레이어를 형제로 분리한다.

영상의 비율과 전체화면은 별개다. 출력 창은 디스플레이를 채우되 영상은 contain/cover를 명시적으로 설정한다. 기존 16:10 영상을 16:9 출력에 맞추면 여백 또는 잘림 중 선택이 필요하다. 해파이는 영상의 여백과 무관하게 설치 영역 전체를 이동한다.

실물 화면 크기가 다르면 해상도 합산만으로 연결하지 않고 물리적 크기 비율·수직 정렬·베젤 간격을 논리 viewport에 반영한다. 겹치는 프로젝터는 별도의 warp/edge blend가 필요하다. 서로 직각인 벽은 관람 위치를 포함한 투영 설계를 추가한다.

## 5. 시간·영상·회차 동기화

기본 제안: A의 길이를 전체 회차의 기준으로 하고 기존 60초 fade / 30초 hold를 유지한다.

| 항목 | 기본 제안 |
|---|---|
| A | 기존 영상, 전체 회차의 기준 미디어 |
| B가 A보다 짧음 | 원래 속도로 반복하다 공통 페이드 적용 |
| B가 A보다 김 | A 회차 종료 시 함께 사라지고 다음 회차에 처음부터 시작 |
| 영상 속도 | 길이를 맞추려고 상시 늘이거나 줄이지 않음 |
| 자막 | 기존 이중 언어 자막은 A에 유지. B 자막은 별도 트랙이 있을 때 연결 |
| 해파이 | 양쪽에서 같은 시간에 등장·유지·제거 |
| 오디오 | 기존 사운드트랙을 A 한 곳에서만 출력. B 영상은 기본 무음 |
| B 파일 미제공 | 개발 미리보기는 검정/테스트 패턴으로 구분. 정식 2채널 시작은 파일 지정 요구 |

상태: PREPARING → ARMED → PLAYING → FADING → HOLD → RESTARTING. 장애 시 PAUSED/RECOVERING으로 전환한다.

- 로딩: 양쪽 모델·미디어 메타데이터·초기 프레임 준비를 보고받는다. canplaythrough만으로 준비 완료를 단정하지 않는다.
- 시작: 메인 단조 시계를 기준으로 미래의 startAt을 전달하고 양쪽을 준비시킨다. 첫 프레임 보고 후 같은 회차를 공개한다. 타이머만으로 물리 동시 출력을 보장한다고 설명하지 않는다.
- 재생: A의 실제 표시된 미디어 시각을 requestVideoFrameCallback 등의 telemetry로 보고받아 기준 showTime을 보정한다. 렌더러별 performance.now()의 원점이 같다고 가정하지 않고 IPC 왕복으로 시계 차이를 추정한다.
- 장면: 이동·유영은 showTime으로 결정한다. 프레임마다 개체 transform 전체를 전송하지 않고 상태 변경과 주기적 시간 anchor만 보낸다.
- B: 목표 localTime=showTime modulo durationB를 기본으로 한다. 미세 편차에는 제한적인 playbackRate 보정, 큰 편차에는 공통 일시정지/재동기화를 사용한다. 임계값은 Windows 실측으로 확정한다.
- A 버퍼링: 공통 showTime을 동결하고 B·해파이도 멈춘다. B 정지 역시 일정 유예 후 두 채널 동결 정책을 기본으로 한다. 소리는 장애 일시정지 때 함께 정지하고 정상 HOLD에서는 계속 재생한다.
- HOLD: A의 마지막 미디어 시각 이후 중앙 단조 시계로 30초를 진행한다.
- 다음 회차: 두 영상 모두 seek 0 및 초기 프레임을 준비한 뒤 전환한다. 한쪽 준비가 늦으면 양쪽 모두 이전 해파이 화면을 유지한다.
- 공통 페이드와 공통 해파이 전환을 유지한다. B 내부 반복은 A 기준 회차 안에서만 허용하며 B 종료 이벤트가 전체 회차를 별도로 전환하지 못하게 한다.

동일 상태·시간을 계산해도 Windows compositor, 출력 포트 및 디스플레이 주사 위상으로 실제 화면에 1프레임 이상 차이가 날 수 있다. Electron의 두 창은 하드웨어 frame lock/genlock 수단이 아니다. 동일 GPU·동일 주사율을 우선 사용하고 고속 촬영으로 경계 통과를 검사한다. 단일 큰 창도 두 물리 출력의 scanout 동기를 보장하지 않는다.

## 6. 문장트리거·트리거영상

- sessionId·eventId 검증, 중복 제거, count/pending 귀속과 ack의 최종 권한은 중앙 컨트롤러에만 둔다.
- 중앙이 이벤트를 수락한 뒤 ack한다. 출력 A/B가 각각 ack하거나 2회 집계하지 않는다.
- 회차 종료 경계와 이벤트 처리는 중앙에서 순서를 정한다. HOLD/복구 중 수신은 pending에 넣어 다음 회차로 넘기는 안을 기본으로 한다.
- 출력 재시작 때 중앙 상태 snapshot을 전달한다. 메인 프로세스 재시작은 신규 세션이며 기존 미확인 이벤트 처리 규칙을 그대로 적용한다. 디스크 영속 이벤트 보존은 별도 범위다.
- 트리거영상·핫핑크 선·기존 문장 레이어는 우선 A에 유지하는 안을 제안한다. 해파이만 전역 연결한다. 이 배치는 미확정이다.
- 추후 트리거영상도 두 채널로 확장하면 중앙이 clip·seed·spawnTime·전역 사각형을 선택하고 양쪽이 같은 효과의 해당 영역을 그린다. 창마다 무작위 영상을 선택하면 안 된다.

현재 iframe URL과 parent origin 검증은 웹 경로에 결합돼 있어 Electron 전용 어댑터가 필요하다. 두 출력에 현재 iframe을 그대로 복제하지 않는다. Game Poem의 이벤트 로직은 재사용하고 접속/렌더 역할을 분리한다.

현재 PeerJS 경로에는 외부 연결 의존성이 있다. 완전 로컬 설치가 필요하면 PC가 태블릿 UI와 WebSocket 이벤트 서버를 LAN에 제공하는 방식을 별도 구현한다. 모바일 태블릿에서 PC의 localhost 주소는 사용할 수 없다. Windows 방화벽·전용 LAN·페어링을 설정하며 인터넷 없이 실제 두 기기에서 검증한다. 기존 웹 PeerJS 경로는 호환 어댑터로 유지할 수 있다.

## 7. Windows 운영과 배포

- 화면 식별 패턴 A/B를 띄워 운영자가 매핑한다. OS의 1/2 번호나 배열 순서만 신뢰하지 않는다. 저장한 displayId·이름·해상도·위치를 대조하고 모호하면 재매핑한다.
- BrowserWindow를 대상 display.bounds에 먼저 배치한 뒤 각각 전체화면으로 전환한다. 실제 전체화면 이벤트를 확인한다. span 대안은 fullscreen:true 대신 합쳐진 bounds의 무테 창을 사용한다.
- 출력은 backgroundThrottling:false를 검토·적용하고 기존 document.hidden 자동 정지 로직을 중앙 명령 기반으로 교체한다. 설정 창 포커스 이동으로 한 채널만 멈추면 안 된다.
- 화면 제거/해상도 변경은 두 출력 공통 일시정지 및 안전 화면으로 처리한다. 자동으로 살아 있는 화면 하나에 두 창을 겹쳐 배치하지 않는다. 재연결·매핑 확인 후 두 채널을 함께 재개한다.
- renderer 장애 시 두 채널을 멈추고 해당 창을 제한 횟수 내 재생성한다. 모델/미디어 준비 후 snapshot·시간을 복원한다. WebGL 컨텍스트 복구와 반복 실패 시 대체 모드를 명시적으로 처리한다.
- 전원 절약 방지, 단일 인스턴스 잠금, 명시적 시작/종료·전체화면 복구 기능을 둔다. Windows 로그인 자동 실행은 설치 설정으로 제공하며 사용자 선택으로 켠다.
- 앱 종료/업데이트는 운영자가 실행한다. 상영 중 자동 재시작 업데이트는 피한다. 프로세스 자체가 죽은 뒤의 자동 재실행은 OS 측 운영 설정이 필요하다.
- 로컬 미디어는 설치 파일과 분리된 media 디렉터리에서 관리한다. assets의 원본 MOV·Blender 파일·preview_frames를 배포 패키지에 전부 포함하지 않는다. 두 영상의 codec/해상도/fps/오디오 존재/체크섬을 사전 검사한다.
- Node 통합은 끄고 contextIsolation:true, sandbox:true 및 좁은 preload API를 사용한다. IPC 발신자와 스키마를 검증하고 임의 파일 읽기·프로세스 실행을 노출하지 않는다.
- Electron용 custom protocol 또는 로컬 HTTP 자산 서버를 사용한다. 허용 경로만 매핑하고 영상 Range/seek·MIME·import map을 테스트한다. 웹 PWA 서비스 워커는 Electron에서는 등록하지 않아 이중 버전 관리를 피한다.
- 설정은 중앙에서 검증하여 userData에 원자적으로 저장한다. renderer localStorage별 설정을 권위 있는 상태로 사용하지 않는다. 설정에는 schemaVersion·A/B 영상 경로·display mapping·논리 viewport·회차/오디오 정책을 포함한다.

보안/로컬 리소스 근거: [Security](https://www.electronjs.org/docs/latest/tutorial/security), [protocol](https://www.electronjs.org/docs/latest/api/protocol). 이 절은 포팅 시 구현 지침이며 이번 설계에서 시스템 설정은 변경하지 않는다.

## 8. 구현 단위와 순서

설계 당시 제안 파일 구조(실제 파일 구성은 구현 기록 및 저장소 참조):

```text
desktop/main/           앱 생명주기·화면·설정·로컬 미디어·상영 컨트롤러
desktop/preload/        명시적 IPC API
desktop/renderer/       출력 화면·운영 화면
shared/show/            회차·이벤트·공통 시계·seed·장면 모델
shared/transports/      Electron IPC / 기존 웹 / LAN 어댑터
video/                  기존 웹 실행 진입점 및 재사용할 렌더링 모듈
```

1. **실제 Windows 기술 검증:** 두 출력의 식별/전체화면, 테스트 영상 2개, 전역 좌표의 단순 도형 경계 통과. 두 창과 단일 span 창의 경계 품질 비교. 이 결과로 창 구조를 최종 확정한다.
2. **공통 장면 분리:** seeded 개체·절대 시간·분할 카메라·SVG 대체·카메라 통과 위치 구현. 기존 cameraPassPosition의 화면 중앙 전제를 하단 B anchor 기준으로 바꾸고 진입 광선과 이동 경로를 함께 계산한다. 기존 한 화면 모드는 전체 viewport로 유지한다.
3. **회차/미디어 동기:** A/B 준비 barrier·시계 보정·공통 fade/hold·재시작·오디오 소유권 구현.
4. **태블릿 통합:** 한 개 어댑터에서 중앙 ack 및 snapshot 전파. Game Poem 변경도 버전을 맞춰 함께 배포한다.
5. **운영 패키지:** 미디어 경로 선택·매핑 저장·오프라인 실행·장애 복구·로그·Windows 패키지 생성.
6. **현장 리허설:** 최종 영상/프로젝터/오디오 장치/태블릿으로 측정 후 설정 고정.

## 9. 검증 기준

- 단위: 동일 seed/time/ID에서 양쪽 transform·mixer 시각 일치, viewport 경계 투영 연속성, 트리거 1회 집계, HOLD 귀속, 시간 정지/재개.
- 브라우저 미리보기: 한 모니터에 두 viewport를 위아래로 띄워 장면 연속성을 비교한다. 이는 Windows 물리 출력 검증을 대체하지 않는다.
- Windows: 두 개 창의 전체화면·재부팅 후 A/B 매핑·포커스 변경·혼합 DPI·케이블 분리/복구·renderer 종료·WebGL 손실.
- 미디어: 짧고 긴 B 영상, seek/loop 경계, 누락/손상 파일, A/B stalled, 다음 회차 첫 프레임에서 이전 해파이 제거.
- 초기 성능 목표: 목표 장비에서 선택한 30 또는 60fps 유지, 16개 해파이·동시 트리거영상 3개 상태의 프레임 시간과 GPU 메모리 측정. 두 4K 출력도 된다고 사전 보장하지 않는다.
- 연속성 목표: 양쪽 showTime 편차와 표시 프레임 지연을 기록하고 경계 촬영에서 식별 가능한 위치/유영 불연속이 없어야 한다. 허용 프레임 차이는 현장 관람 거리·이동 속도로 확정한다.
- 최소 8시간 또는 실제 하루 운영 시간 중 더 긴 시간 동안 반복·메모리 증가·오디오 중복·카운트 누락을 확인한다.
- 오프라인 요구가 확정되면 WAN을 끊은 상태에서 앱 부팅부터 태블릿 입력까지 검증한다.

## 10. 구현 전 확정할 정보

필수: PC가 한 대인지, 두 화면의 실물 크기와 간격, 해상도/주사율, GPU/Windows 사양, 기존 영상 A를 회차 기준으로 사용할지 여부. 상하 배치와 공통 페이드/해파이 전환은 확정됐다.
영상 B 제공 시: 길이·codec·프레임률·종횡비·음원·자막.
확정 화면 매핑: A=위(기존 영상), B=아래(새 영상).
연출 선택: 서로 다른 영상 길이 처리, 첫 카메라 통과 해파이 위치, 트리거영상/문장을 A에 유지할지 양쪽으로 확장할지, 베젤/프로젝터 중첩 처리.
운영 선택: 인터넷 없는 태블릿 연결 필요 여부, 자동 실행, 하루 상영 시간, 장애 시 자동 재개 범위.

권장 결정은 Electron 채택과 공통 장면/중앙 컨트롤러 구조이며, 두 창을 사용할지 단일 span 창을 사용할지는 첫 Windows 경계 통과 검증에서 최종 확정한다.
